# FEAT-36: Invitation codes that unlock Plus for friends

> Implements: INV-01..07 (D25; plan row FEAT-36 in `05-phase3-plan.md`) · Uses: ENT-01/03 (`entitlements` with `source = invite`, `GET /api/nn/entitlement`, FEAT-29), PLS-01/07 (SCR-20, `PlusController`, FEAT-30) · Fixes: FEAT-30 verify follow-up (launch bank check sees Plus late) · Screens: SCR-20 gains "Have an invitation code?"
> Status: designed · Branch: `feat/FEAT-36-invite-codes` · 2026-11-20 (auto mode: decisions below taken by Claude on Ken's standing instruction)

## Scope

Ken makes batches of short codes; a friend's parent, signed in, types one on SCR-20 and the family gets Plus for the code's length (default 12 months). Each code has a use limit (default 5 families) and a last day it can be redeemed. The server checks and counts every redemption and writes the family's `invite` entitlement (FEAT-29), so every existing Plus rule (bank gate, app cache, 7-day grace, downgrade without deleting, PD-6) applies unchanged; when it runs out the family is simply free again. On iOS the code box is hidden (App Store guideline 3.1.1); iPhone and iPad friends get Apple offer codes in FEAT-34. Also fixes FEAT-30's follow-up: the launch bank check waits for the Plus cache.

Not in scope: Apple offer codes (FEAT-34), store purchases (FEAT-35), a web page to redeem codes (the app is the only place), referral rewards, codes for anything but Plus.

## Design decisions (this feature)

Auto mode (Ken, 2026-11-20): each takes the recommended option; the reason follows the dash.

- **IC-1 Code shape.** 8 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (32 symbols: no 0/O, 1/I), shown and printed as `ABCD-EFGH`. Input is upper-cased and every character outside the alphabet (space, dash) is dropped before checking; `O`, `0`, `I` and `1` are not code characters, so a mistyped code stays short and "Use code" stays off. — 32⁸ ≈ 1.1 × 10¹² codes: with the IC-5 limit and even 1,000 live codes a guesser needs thousands of years, so no per-account lockout table is needed.
- **IC-2 Collection `invite_codes`** (superuser only: every rule `null`): `code` (text, exactly 8, unique index), `months` (number 1..24, default 12), `max_uses` (number 1..100, default 5), `uses` (number, starts 0), `redeem_by` (date, required; default 365 days after making), `note` (text ≤ 200, Ken's words like "school friends"), `revoked` (bool), autodate `created`/`updated`. Codes are stored as plain text, not hashed — Ken must be able to read them in the PocketBase admin, and a code is worth at most a year of Plus. Revoking a code stops new redemptions only; families who already redeemed keep their Plus until it ends (Ken can still revoke a family's Plus with `grant_plus.dart`-style edits in the admin).
- **IC-3 Collection `invite_redemptions`** (superuser only): `code` → invite_codes (cascade delete), `user` → users (cascade delete, so ACC-07 removes it), `plus_until` (date), autodate `created`; unique index `(code, user)`. — Proves who used which code, stops one family using the same code twice, and lets Ken see a code's families. `invite_codes.uses` is the counter (it does not go down when an account is deleted: the use was spent).
- **IC-4 Redeem endpoint** `POST /api/nn/invite/redeem` `{code}`, `$apis.requireAuth("users")`, and the account must be verified (`e.auth.verify()` false → 403 `unverified`; same rule as child data, keeps throwaway accounts out). One transaction: normalise (IC-1), find the code; then in this order → 400 `{reason}`: `not_found` (unknown or revoked), `expired` (`redeem_by` past), `used_up` (`uses >= max_uses`), `already_used` (this account redeemed this code), `already_plus` (the account has an active entitlement from any source **other than** `invite`: a gift or a store subscription; no use is spent). Success: `uses + 1`, a redemption row, and the account's `invite` entitlement (upsert on `(user, invite)`, FEAT-29 AD-1) gets `expires_at = addMonths(max(now, current invite expires_at), months)` (calendar months in UTC, day clamped to month end), `status active`, `note = "invite <code>: <code note>"`; response 200 = the `GET /api/nn/entitlement` body (AD-5), so the app can show the new state at once. — A second, different code extends an invitation (a friend can top up), but never stacks on a gift or a store subscription, where it would waste a use.
- **IC-5 Rate limit.** Rate-limit rule `/api/nn/invite/` 5 requests per 60 s (per client, like FEAT-14/24/29 rules) added by the migration. Wrong guesses get the same 400 as any other failure. — See IC-1 for why this is enough.
- **IC-6 Making codes: a superuser endpoint, a tool and a workflow.** `POST /api/nn/admin/invites` (superuser only) `{count 1..100, months, max_uses, redeem_by_days, note, send_to?}` makes the codes (`$security.randomStringWithAlphabet(8, alphabet)`, retried on a unique clash) and returns them; with `send_to` (or env `INVITE_MAIL_TO`, falling back to `CRASH_DIGEST_TO`) it also emails the list through the normal mail path (Resend, FEAT-13) with the note, length, uses and last redeem day, and the response then omits the codes. `tool/make_invites.dart --count N [--months 12] [--uses 5] [--days 365] --note TEXT [--send-to EMAIL] [--print] [--server URL]` (superuser from `PB_SUPERUSER_EMAIL`/`PB_SUPERUSER_PASSWORD` like `grant_plus.dart`) prints one summary line, plus the codes only with `--print`. Also `--list [--note TEXT]` (code, uses/max, redeem by, revoked) and `--revoke CODE`. Workflow `make-invites.yml` (`workflow_dispatch`: count, months, uses, days, note, send_to masked) runs the tool **without** `--print`. — The repo is public, so CI logs are public: codes never appear in a log. Ken gets them by email or reads them in the PocketBase admin (`invite_codes`, filter by note); the README says both.
- **IC-7 Defaults are the plan's.** 12 months of Plus, 5 families per code, redeemable for 365 days. Ken picks who gets codes (no change to the plan's "Ken's hands": decide who gets them and run the workflow).
- **IC-8 SCR-20 "Have an invitation code?"** A row under the status card, shown when signed in, invitations are allowed (IC-9) and Plus is not active from another source (free, or Plus from an invitation: the row then reads "Have another invitation code?"). Tapping opens a dialog: one text field (`TextCapitalization.characters`, hint `ABCD-EFGH`, accepts 8 code characters with or without the dash), "Use code" (enabled at 8 valid characters) and "Cancel". While sending: "Checking…". Success: the dialog closes, the returned entitlement goes into the Plus cache (then `plusControllerProvider.notifier.check()` to follow the normal path) and a snack bar says "Plus until <date>, from an invitation. Enjoy!". Errors stay in the dialog, one line each: not_found "We couldn't find that code. Check the letters and try again."; expired "This code has expired."; used_up "This code has been used by as many families as it allows."; already_used "You've already used this code."; already_plus "You already have Plus, so keep this code for another family."; unverified "Please verify your email first (see Account)."; 429 "Too many tries. Wait a minute and try again."; offline/5xx "Couldn't reach BrainBubblz. Check the internet and try again." Inside the PIN area only (SCR-20 already is); the child never sees codes.
- **IC-9 Hidden on iOS.** `inviteCodesAllowedProvider` (bool) = `defaultTargetPlatform != TargetPlatform.iOS && != TargetPlatform.macOS`; tests override it. The server doesn't need to know the platform: an iOS build has no way to send a code. — Apple guideline 3.1.1 forbids unlocking features with the app's own codes; FEAT-34 adds Apple offer codes.
- **IC-10 Status line for invitations.** `plusStatusLine`: source `invite` → "Plus until <date>, from an invitation". When Plus is off and the cache has `ended_at`, the free line adds "Plus ended on <date>." (any source; nothing else changes on downgrade, PD-6).
- **IC-11 Server client.** `ServerClient.redeemInvite(String code)` → `InviteResult` (`ok(Entitlement)` or `failed(InviteFailure)` with `notFound, expired, usedUp, alreadyUsed, alreadyPlus, unverified, tooMany, offline`); `FakeServerClient` gets `inviteResult` (settable) and `redeemCalls`. `PlusRepository.storeEntitlement(accountId, Entitlement)` writes the cache row the same way `refresh` does (shared private helper).
- **IC-12 Launch bank check waits for Plus** (FEAT-30 verify follow-up). `checkBank` first `await ref.read(plusCacheProvider.future)` (errors ignored), then reads `bankUpdaterProvider`, so the launch check of a Plus family no longer returns `noPlus` while the cache loads. The code-map gotcha line is updated to say it's fixed.

## Acceptance criteria

- **AC-1** (INV-01, IC-2, IC-3): rule tests: a guest and a signed-in parent can't list, view, create, update or delete `invite_codes` or `invite_redemptions` (empty list / 403 / 404); a superuser can; `code` is unique; deleting a user deletes their redemptions, not the code.
- **AC-2** (INV-02, IC-4): redeem as a verified parent with no Plus: 200, body `plus true, source invite, until` = now + 12 months (UTC, to the millisecond); `uses` is 1; one redemption row; `GET /api/nn/entitlement` agrees; the bank list is now visible (BNK-13). Lower-case input with spaces and a dash works.
- **AC-3** (INV-03, IC-4): failures, each writing nothing and leaving `uses` unchanged: guest → 401; unverified → 403; unknown, revoked → `not_found`; `redeem_by` past → `expired`; a 2-use code after two families → `used_up` for a third; the same family twice → `already_used`; a family with complimentary FOREVER or an active `google_play` record → `already_plus`.
- **AC-4** (INV-03, IC-4): a family with invite Plus ending in 2 months redeems a second 3-month code → `until` = old end + 3 months; a family whose invite Plus ended last month → now + months (not stacked on the past). `addMonths` clamps 31 Jan + 1 month to 28/29 Feb (unit check in the same test file through the endpoint dates).
- **AC-5** (INV-04, IC-5): the 6th redeem call within 60 s gets 429.
- **AC-6** (INV-05, IC-1, IC-6): admin endpoint: a parent → 401/403; superuser with count 10 → 10 unique 8-character codes, all from the alphabet, with the given months, uses, note and `redeem_by`; with `send_to` one email reaches the test mail sink listing the 10 codes and the response has no codes. `make_invites_test.dart`: `--count 3 --print` prints 3 `XXXX-XXXX` codes; without `--print` stdout contains no code; `--list --note` shows them with `0/5`; `--revoke` makes a code `not_found` for redeem.
- **AC-7** (INV-06, IC-8, IC-11): widget tests on SCR-20 with `FakeServerClient`: signed in and free → row "Have an invitation code?"; the dialog's button is off until 8 valid characters; success closes the dialog, shows "Plus until …, from an invitation", and Plus features open (e.g. SCR-09 day card); each failure reason shows its line and keeps the dialog open; signed out → no row; complimentary Plus → no row; invite Plus → "Have another invitation code?".
- **AC-8** (INV-07, IC-9): with `inviteCodesAllowedProvider` false (iOS) SCR-20 shows no code row, signed in and free.
- **AC-9** (IC-10): `plusStatusLine` unit tests: invite source → "Plus until <date>, from an invitation"; free with `ended_at` → free line plus "Plus ended on <date>."
- **AC-10** (IC-12, BNK-13): with Plus in the cache, a launch `checkBank` started before the cache has loaded calls the server (not `noPlus`); free → `noPlus` without a server call (FEAT-30 AC-8 still holds).
- **AC-11** (live, with the M9 release, not needed to merge): Ken makes one code with the workflow on `api.brainbubblz.com`, receives it by email (or reads it in the admin), and a test account redeems it on a tablet.
