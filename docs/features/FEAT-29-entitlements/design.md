# FEAT-29: Entitlements on the server

> Implements: ENT-01..06, BNK-13 (D23; ADR-09, ADR-10 in `05-phase3-plan.md`) · Touches: BNK-08 (server bank now needs Plus), ACC-07 (account delete removes entitlements), NFR-13 (rules as code, rule tests), NFR-15 · Screens: none (the Plus screen is FEAT-30)
> Status: designed · Branch: `feat/FEAT-29-entitlements` · 2026-11-20 (auto mode: decisions below taken by Claude on Ken's standing instruction)

## Scope

The server learns who has BrainBubblz Plus. A new `entitlements` collection holds one record per parent account and source (complimentary, invite, Google Play, App Store) with an expiry; Plus is active while any of the account's records expires in the future. The server bank (FEAT-15) becomes the first thing gated: listing banks and downloading a bank file need a signed-in parent with active Plus; everyone else keeps the bundled bank. The app reads its Plus state from one endpoint (`GET /api/nn/entitlement`, used by FEAT-30). A webhook for the billing service (RevenueCat, ADR-09) updates store records once FEAT-35 connects real purchases; until then it is built and tested with fixture events and stays off. Complimentary grants come from the PocketBase admin or a repo script and workflow; every account that exists when this deploys (Ken's family) gets Plus with no end date.

Not in scope: any app UI or caching of Plus (FEAT-30), invitation codes (FEAT-36 writes `source = invite` records through this collection), RevenueCat account, store products and real purchases (FEAT-35, M10), gating anything but the bank on the server (on-device Plus features are gated in the app, ADR-10).

## Design decisions (this feature)

Auto mode (Ken, 2026-11-20): each takes the recommended option; the reason follows the dash.

- **AD-1 One record per account and source, expiry decides** (plan row). Fields: `user` → users (required, cascade delete, so ACC-07 removes them), `plan` (select: `plus`), `source` (select: `complimentary`, `invite`, `google_play`, `app_store`), `status` (select: `active`, `cancelled`, `billing_issue`, `paused`, `expired`, `refunded`, `revoked`), `expires_at` (date, required), `note` (text ≤ 200, admin's words like "Ken's family"), `product_id`, `environment` (text ≤ 64), `last_event_id` (text ≤ 128), `last_event_at` (date), autodate `created`/`updated`; unique index `(user, source)`. **Plus is active ⇔ some record has `expires_at > now`.** `status` is information for the app's wording (FEAT-30: "won't renew", "payment problem"), never part of the check — one comparable field keeps the API rule and every test simple. "No end" is `expires_at = 2099-12-31 23:59:59Z` (constant `FOREVER`). Revoking sets `expires_at = now` and `status = revoked`; nothing is deleted, so history stays.
- **AD-2 Only the server writes entitlements.** List/view rule `user = @request.auth.id`; create, update and delete rules `null` (superuser, hooks, the grant script). A parent can read their own records and nobody else's (NFR-13).
- **AD-3 Gate the bank with an API rule, not a hook.** `banks` list and view rule: `@request.auth.collectionName = "users" && @collection.entitlements.user ?= @request.auth.id && @collection.entitlements.expires_at ?> @now`. The two conditions on the same `@collection` reference join the same row in PocketBase (an alias would be needed for different rows); AC-3 proves it with a user whose only active record belongs to someone else. If PocketBase 0.40.6 behaves otherwise, fall back to a `users.plus_until` date kept by an `entitlements` hook and rule `@request.auth.plus_until > @now` (users' update rule then refuses `plus_until`), and note the deviation in the handoff. Anonymous and free callers get an empty list (200), which the app already treats as "no newer bank" (BNK-08 keeps the current bank), so v2.2.0 tablets degrade quietly.
- **AD-4 Protect the bank file too.** The `banks.file` field becomes `protected: true`, so the URL alone no longer downloads it; PocketBase then needs a short-lived file token whose holder passes the view rule. `PocketBaseServerClient.latestBank` asks for a token (`pb.files.getToken()`) when signed in and builds `fileUrl` with it; `downloadBank` is unchanged (BankUpdater downloads right after the check, well inside the token's life). This is the only app change in FEAT-29 and keeps the gate real (ADR-10: the server protects what costs us).
- **AD-5 One read endpoint for the app.** `GET /api/nn/entitlement` (signed-in user, else 401) returns `{plus, until, source, status, will_renew, ended_at, checked_at}`: `plus` and the fields of the active record with the latest `expires_at` (`will_renew` = store source and status `active`); with no active record `plus = false` and `ended_at` = latest past expiry or null; `checked_at` = server time, so FEAT-30's 7-day offline grace and clock-skew check have a trusted reference. Logic lives in one place (`pb_hooks/entitlement.pb.js`, shared helper `activeEntitlement(app, userId, now)`), not in the app.
- **AD-6 RevenueCat webhook, off until FEAT-35** (ADR-09). `POST /api/nn/billing/revenuecat`. `Authorization` must equal `BILLING_WEBHOOK_SECRET` exactly (RevenueCat sends the configured header value); wrong or missing → 401; env unset → 503 (endpoint disabled), so nothing can write store entitlements until Ken creates the RevenueCat account in M10. Rate limit `/api/nn/billing/` 60 per 60 s. No secret is needed to ship FEAT-29.
- **AD-7 Webhook event mapping.** User: first of `app_user_id`, `original_app_user_id`, `aliases[]` that is a `users` id (FEAT-35 logs RevenueCat in with the PocketBase user id); none → 200 `{"ignored":"unknown user"}` (a non-200 makes RevenueCat retry for days). Store: `PLAY_STORE` → `google_play`, `APP_STORE` → `app_store`, anything else → 200 ignored. Only events whose `entitlement_ids` include `plus` (or have none, like TRANSFER) count. `INITIAL_PURCHASE`, `RENEWAL`, `UNCANCELLATION`, `PRODUCT_CHANGE`, `NON_RENEWING_PURCHASE`, `SUBSCRIPTION_EXTENDED`, `TEMPORARY_ENTITLEMENT_GRANT` → `active`, `expires_at = expiration_at_ms` (null → `FOREVER`). `CANCELLATION` → `cancelled` (`refunded` when `cancel_reason` is `CUSTOMER_SUPPORT`), expiry from the event (a refund's expiry is in the past, so Plus ends). `BILLING_ISSUE` → `billing_issue`, expiry = `grace_period_expiration_at_ms` if given. `SUBSCRIPTION_PAUSED` → `paused`, expiry unchanged. `EXPIRATION` → `expired`, expiry = min(event expiry, now). `TRANSFER` → each `transferred_from` user's record of that store is copied to the `transferred_to` user and the old one set `expired` now. `TEST` and unknown types → 200 ignored. Upsert on `(user, source)`; `product_id`, `environment` stored. Sandbox events are accepted and marked by `environment` (closed-test license testers need them, FEAT-35 may tighten).
- **AD-8 Idempotent and ordered.** Same `event.id` as `last_event_id` → 200, no change. `event_timestamp_ms` older than `last_event_at` → 200, no change (RevenueCat may deliver out of order). Each event is one transaction.
- **AD-9 Complimentary grants from the repo.** `tool/grant_plus.dart --email E (--until YYYY-MM-DD | --forever | --revoke) [--note N] [--server URL]`, superuser from `PB_SUPERUSER_EMAIL`/`PB_SUPERUSER_PASSWORD` like `tool/publish_bank.dart`; upserts the account's `complimentary` record and prints `plus until <date>` (never the email). Workflow `grant-plus.yml` (`workflow_dispatch`: email, until, note, revoke) masks the email with `::add-mask::` so it isn't in the log. Ken can also edit the record in the PocketBase admin; the README says how.
- **AD-10 Ken's family keeps Plus with nothing to do.** The migration gives every `users` record that exists when it runs a `complimentary` record, `expires_at = FOREVER`, `note = "founding family (FEAT-29)"`. Today the only accounts are Ken's family and test accounts on his own server (the app isn't public), so this is exactly "Ken's family keeps Plus free" without anyone typing an email. Accounts created later start free. The migration's down step deletes only records with that note.
- **AD-11 No new secret for Ken now.** `deploy-server.yml` passes `BILLING_WEBHOOK_SECRET` (optional secret, empty is fine) into the server env next to the others; FEAT-35 sets it. The plan row's "Ken's hands" (billing account, webhook secret) therefore moves to FEAT-35.

## Acceptance criteria

- **AC-1** (ENT-01, ENT-02): rule tests: a parent lists and views only their own entitlements; a guest sees none; parents (own or other) can't create, update or delete one (403/404); a superuser can; deleting the user deletes their entitlements; `(user, source)` is unique.
- **AC-2** (BNK-13): as superuser publish a bank; a guest and a signed-in parent with no entitlement list 0 banks; the same parent with a complimentary record expiring tomorrow lists it and downloads the file with a file token; without a token the file URL is refused; after `expires_at` is set to the past the list is empty again.
- **AC-3** (BNK-13, AD-3): parent A has an expired record and parent B an active one: A lists 0 banks (the join doesn't mix rows).
- **AC-4** (ENT-03): `GET /api/nn/entitlement`: guest → 401; no records → `plus false, ended_at null`; complimentary FOREVER → `plus true, until 2099-12-31…, source complimentary, will_renew false`; an expired store record plus an active complimentary one → the complimentary one; only expired → `plus false, ended_at` = that expiry; `checked_at` within a few seconds of the test clock.
- **AC-5** (ENT-04): webhook with fixture events: no secret configured → 503; wrong or missing header → 401; INITIAL_PURCHASE (PLAY_STORE) creates an active `google_play` record with the event's expiry and the endpoint then says `will_renew true`; RENEWAL extends it; CANCELLATION → `cancelled`, still Plus until expiry; refund CANCELLATION in the past → Plus off; EXPIRATION → off; the same event id twice changes nothing; an older event after a newer one changes nothing; unknown user, unknown store, other entitlement id and TEST → 200 with nothing written; TRANSFER moves the record.
- **AC-6** (ENT-05): `grant_plus_test.dart`: `--forever` creates a FOREVER complimentary record; `--until 2027-06-30` updates the same record (no second one); `--revoke` sets it expired now with status `revoked`; an unknown email exits non-zero and writes nothing; the email never appears in stdout.
- **AC-7** (ENT-06): migration test in `run.sh`: users created before the migration runs get one FOREVER complimentary record each with the founding note; a user created after has none. (Run by starting the local PocketBase on a data dir seeded with users through the previous migrations, then applying the new one.)
- **AC-8** (BNK-13, app): `server_client` test with a mocked HTTP client: signed in, `latestBank` asks for a file token and the `fileUrl` carries `token=`; signed out it makes no token call. `bank_live_test.dart` passes against the local server with a granted parent.
- **AC-9** (live, after deploy): Ken's account on `api.brainbubblz.com` reports `plus true` from the endpoint (checked by the verify or merge thread with the superuser in the admin API or by the founding record existing); Ken's v2.2.0 tablet still opens and plays (bank list just empty if signed out). Not required to merge.
